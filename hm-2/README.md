# ДЗ-2. Marketplace: OpenAPI + CRUD

Один backend на Python / FastAPI и PostgreSQL. Контракт написан вручную в OpenAPI, а маршруты и DTO создаются генератором. Миграции выполняет Flyway. Реализованы товары, заказы, промокоды, JWT и роли.

## Запуск

Нужен Docker Desktop в режиме Linux containers. Выполняйте команды из `hm-2`:

```powershell
cd "C: курс\Архитектура\marketplace-design\hm-2"
docker compose up -d --build
docker compose ps -a
```

Первый запуск скачивает образы и зависимости. `db` и `api` должны быть `healthy`. `migrate` завершается с кодом 0 — это нормально: он выполнил миграцию и больше не нужен.

- Swagger UI: http://localhost:8001/docs
- Проверка приложения и БД: http://localhost:8001/health
- Контракт: `openapi/marketplace.json`

```powershell
curl.exe -i http://localhost:8001/health
docker compose logs --tail 20 api
docker compose logs migrate
```

Порт компьютера — 8001, внутри контейнера — 8000. Это позволяет не занимать порт ДЗ-1.

## Демонстрационные пользователи

На старте создаются три учётные записи. Общий пароль: `DemoPass123!`.

| Email | Роль |
|---|---|
| `admin@example.com` | ADMIN |
| `seller@example.com` | SELLER |
| `user@example.com` | USER |

Публичная регистрация создаёт только USER. Передать себе роль ADMIN через регистрацию нельзя. Пароли хранятся как PBKDF2-хеши с индивидуальной случайной солью. Учётные записи и секрет из Compose предназначены для локальной учебной демонстрации.

## Быстрая демонстрация в Swagger

1. Откройте `/auth/login`, нажмите **Try it out** и отправьте email продавца и пароль.
2. Скопируйте `access_token`. Нажмите **Authorize**, вставьте токен без префикса `Bearer`.
3. Создайте товар через `POST /products`:

```json
{
  "name": "Футболка",
  "description": "Хлопок, размер M",
  "price": 1500,
  "stock": 10,
  "category": "Одежда",
  "status": "ACTIVE"
}
```

4. Проверьте товар через `GET /products/{id}` и список через `GET /products`. Можно задать `page`, `size`, `status`, `category`.
5. Войдите покупателем через `/auth/login` и замените токен в **Authorize**.
6. Создайте заказ через `POST /orders`, подставив полученный ID товара:

```json
{
  "items": [
    {"product_id": 1, "quantity": 2}
  ]
}
```

7. Проверьте, что остаток уменьшился, а в заказе сохранена цена. Отмените заказ через `POST /orders/{id}/cancel`: остаток восстановится.
8. Повторная отмена вернёт `409 INVALID_STATE_TRANSITION`.

ID в примере условный: используйте ID из своего ответа. Если у демонстрационного покупателя уже есть активный заказ, отмените его или зарегистрируйте нового пользователя. После успешного создания следующий заказ доступен через минуту, даже если старый отменён.

## Показать данные в PostgreSQL

Для защиты недостаточно показать HTTP-ответы — выполните SELECT:

```powershell
docker compose exec db psql -U marketplace -d marketplace -c "SELECT id,name,price,stock,status,seller_id FROM products ORDER BY id;"
docker compose exec db psql -U marketplace -d marketplace -c "SELECT id,user_id,status,total_amount,discount_amount,promo_code_id FROM orders ORDER BY id;"
docker compose exec db psql -U marketplace -d marketplace -c "SELECT * FROM order_items ORDER BY id;"
docker compose exec db psql -U marketplace -d marketplace -c "SELECT code,current_uses,max_uses FROM promo_codes;"
docker compose exec db psql -U marketplace -d marketplace -c "SELECT * FROM user_operations ORDER BY id;"
docker compose exec db psql -U marketplace -d marketplace -c "SELECT version,description,success FROM flyway_schema_history;"
```

## Автоматическая сквозная проверка

После запуска Compose выполните (нужен Python на компьютере):

```powershell
python tools/check_e2e.py
```

Проверяются CRUD, фильтры, валидация, ошибки, права, JWT, остатки, снимки цен, промокоды, обновление и отмена заказа, модель состояний. Есть параллельная покупка последнего товара и конкуренция за последнее использование промокода.

Тесты работают с настоящими HTTP-запросами и PostgreSQL. Они создают уникальные тестовые записи и не удаляют существующие данные. Для проверки двух разных ошибок тест сдвигает время операций только своего тестового пользователя: иначе минутный лимит скрывал бы ошибку наличия активного заказа. Для тестов используется стандартный интервал 1 минута.

## 1–2. OpenAPI и схемы

Описаны все операции Product, пагинация с нулевой страницы и размером 20, точные фильтры статуса и категории. Ответ списка содержит `items`, `totalElements`, `page`, `size`. Товары сортируются по ID. Архивные товары остаются доступны для чтения; исключить их можно фильтром.

Есть отдельные ProductCreate, ProductUpdate и ProductResponse. PUT полностью заменяет изменяемые поля. Если description не передан, он очищается. ID и даты назначает сервер. `seller_id` можно не передавать: будет выбран текущий продавец; ADMIN может указать другого существующего продавца.

## 3. Генерация

```powershell
python tools/generate.py
```

Сначала спецификация проверяется, затем создаются обработчики FastAPI и модели Python. Для точных денег модели генерируются с Decimal. Постобработка снимает только строгий запрет преобразования входного числа для Decimal-полей, сохраняя ограничения. При сборке Docker выполняются те же шаги автоматически. Локальная папка generated в образ не копируется.

Генератор предоставляет маршруты и базовый класс API. `app/api/implementation.py` реализует его методы. Модели используются для входной валидации и проверки исходящих данных. Ответы сериализуются через simplejson: Decimal остаётся JSON-числом, без промежуточного float. Запросы с денежными значениями в виде строк отвергаются.

## 4. PostgreSQL и миграции

Схему создаёт контейнер Flyway перед запуском API. История хранится в flyway_schema_history. SQL передаётся инструменту миграций, а не выполняется вручную при каждом старте приложения. Статус товара индексирован; даты назначаются БД и обновляются триггером. DELETE переводит товар в ARCHIVED.

## 5–6. Ошибки и валидация

Ошибки имеют поля `error_code`, `message` и необязательное `details`. Каталог и HTTP-статусы описаны в OpenAPI. Невалидные данные возвращают 400 VALIDATION_ERROR с полями и причинами. Обязательные длины, диапазоны, enum, шаблон промокода и размер массива позиций заданы в спецификации и переносятся в модели генератором.

Цена ограничена двумя знаками после запятой и диапазоном DECIMAL(12,2). Для query-параметра status есть дополнительная проверка, потому что генератор FastAPI создаёт для него обычную строку.

## 7. Заказы и транзакции

Операции создания, обновления и отмены выполняются в одной транзакции через контекст соединения psycopg. Исключение откатывает все изменения. Товарные строки блокируются FOR UPDATE по возрастанию ID: это предотвращает одновременное списание одного остатка двумя заказами. Строка пользователя блокируется для последовательной проверки лимита, а частичный уникальный индекс дополнительно запрещает два активных заказа.

Создание последовательно проверяет частоту, наличие активного заказа, товары и остатки. Фиксируются цена и количество, вычисляется сумма и скидка, сохраняется операция. При ошибке промокода резервирование тоже откатывается. Повторяющиеся ID товара объединяются перед проверкой общего количества.

Обновление разрешено только в CREATED. Старые остатки возвращаются и новые резервируются в одной транзакции; новые позиции получают текущие цены. Если новая сумма ниже минимума промокода, он снимается и использование возвращается. Остальные причины невалидности промокода приводят к ошибке с откатом. Отмена доступна из CREATED и PAYMENT_PENDING и возвращает остатки и использование промокода.

Статусы: CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED. Для демонстрации переходов добавлен `PUT /orders/{id}/status`, доступный ADMIN. Это учебная смена состояния, не интеграция с настоящим платёжным провайдером. Отмена выполняется отдельной операцией /cancel.

Неоднозначность условия про процентную скидку трактуется так: если она превышает 70%, скидка равна нулю, покупатель платит полную цену. Ровно 70% разрешено. Фиксированная скидка не превышает сумму заказа. Денежные результаты округляются до копеек ROUND_HALF_UP. При обновлении существующее использование промокода не считается новым и не увеличивает счётчик повторно.

## 8. Логирование

Каждый HTTP-запрос имеет JSON-запись: request_id, method, endpoint, status_code, duration_ms, user_id, timestamp. Для POST/PUT/DELETE добавляется request_body. Пароли, токены и секреты маскируются. UUID возвращается в X-Request-Id. Служебные сообщения запуска Uvicorn могут быть обычным текстом; записи запросов имеют JSON-формат.

## 9–10. Авторизация и роли

Access JWT действует 20 минут, refresh JWT — 14 дней. Оба подписаны HS256 и содержат тип токена. Refresh нельзя использовать как access и наоборот. Проверяются подпись, срок, обязательные claims, наличие пользователя и его актуальная роль. Refresh выдаёт новую пару; отзыв старых refresh-токенов не реализован и условием не требуется.

USER читает товары и работает со своими заказами. SELLER читает товары, изменяет только свои и создаёт промокоды; заказы ему запрещены. ADMIN управляет любыми товарами и заказами. Роли находятся в JWT и проверяются сервером, а не только в интерфейсе Swagger.

## Настройки и остановка

`ORDER_INTERVAL_MINUTES` задаёт минимальный интервал между успешными CREATE_ORDER и, отдельно, UPDATE_ORDER. Значение по умолчанию — 1. `JWT_SECRET` задаёт ключ подписи. Переменные можно задать в файле `.env` рядом с Compose; пример — `.env.example`.

```powershell
docker compose down
```

Данные сохраняются в volume PostgreSQL. Следующий `docker compose up -d --build` запустит ту же БД. Для полного удаления учебной БД существует `docker compose down -v`; эта команда удаляет все данные именно этого Compose-проекта.

# Подготовка к защите

## Последовательность показа

1. В `hm-2` выполнить `docker compose up -d --build`, показать `docker compose ps -a` и `docker compose logs migrate`.
2. Открыть `http://localhost:8001/docs`, войти продавцом, создать и получить товар.
3. Войти покупателем, создать заказ. Сравнить stock до и после и price_at_order.
4. Выполнить SELECT через `docker compose exec db psql` (команды в README).
5. Показать 400 для отрицательного stock, 403 для создания товара покупателем и 409 для нехватки остатка.
6. Отменить заказ и показать восстановление stock. Показать JSON-логи и X-Request-Id.
7. При необходимости запустить `python tools/check_e2e.py` — проверки занимают несколько секунд и оставляют тестовые данные.

## Что объяснить в коде

- **Contract-first:** сначала marketplace.json, затем генерация. DTO и маршруты не пишутся вручную.
- **CRUD:** create/read/update/delete. DELETE мягкий — меняется статус, строка остаётся.
- **Маршрут и реализация:** generated принимает запрос, app/api/implementation.py вызывает services.py.
- **Pydantic:** проверяет типы и ограничения из сгенерированной модели до бизнес-операции.
- **Транзакция:** либо все изменения заказа и остатков фиксируются, либо всё откатывается. В коде это `with connect() as db`.
- **FOR UPDATE:** конкурентный запрос ждёт освобождения товарной строки, затем видит актуальный остаток.
- **Decimal и NUMERIC:** точные десятичные вычисления в Python и PostgreSQL. float может давать погрешности.
- **Snapshot:** price_at_order сохраняет цену покупки; изменение products.price не меняет старые позиции.
- **Миграция Flyway:** версия SQL применяется один раз, результат и контрольная сумма записываются в flyway_schema_history.
- **JWT:** подписанные claims. Подпись проверяет целостность, но содержимое токена не зашифровано.
- **Access/refresh:** access для операций API, refresh для получения новой пары. Типы проверяются отдельно.
- **401/403:** 401 — нет корректного токена, 403 — пользователь известен, но нет прав.
- **Роли и владелец:** одной роли SELLER мало — seller_id товара должен совпадать с текущим пользователем.
- **Пароли:** PBKDF2 с солью, сравнение хешей через compare_digest. Исходный пароль в БД не сохраняется.
- **Middleware:** выполняет общую работу вокруг запроса: идентификатор, проверка токена, измерение времени, лог.
- **Docker build/run:** build собирает образ, Compose запускает API, PostgreSQL и разовый процесс миграций.

## Принятые решения

Один монолит, обычный SQL через psycopg, без ORM и микросервисов. Это позволяет непосредственно показать транзакции и SELECT. Синхронные запросы к БД выполняются в thread pool, чтобы не блокировать цикл обработки FastAPI. Запросы параметризованы через %s; значения не подставляются в SQL строковой конкатенацией.

Процент свыше 70% означает полную цену, согласно фразе условия «в ином случае цена 100%». Статусы меняет ADMIN через дополнительный endpoint. SELLER и ADMIN создаются как учебные аккаунты; публичная регистрация выдаёт USER.

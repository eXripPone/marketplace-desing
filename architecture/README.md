# Архитектура маркетплейса

Выбрана архитектура модульного монолита: одно backend-приложение обслуживает все домены. Домены разделены по ответственности, но не запускаются как отдельные сервисы.

На диаграмме [C4 Context](C4%20Context.pdf) показаны покупатель, продавец, маркетплейс и внешняя система оплаты. На [C4 Containers](C4%20Containers.pdf) раскрыты три контейнера: веб-приложение React, backend Python / FastAPI и база PostgreSQL. Уведомления отображаются внутри приложения.

## 3. Домены и их ответственность

| Домен | Ответственность |
|---|---|
| Пользователи | Учётные записи покупателей и продавцов. |
| Каталог | Товары продавцов, названия, описания, категории, характеристики и текущие цены. |
| Рекомендации | Персональная лента на основе поисковых интересов и прошлых покупок. |
| Заказы | Состав заказа, количество товаров, итоговая сумма и статус. |
| Платежи | Сумма к оплате  из заказа, обращение к провайдеру и учёт результатов оплаты. |
| Уведомления | Хранение сообщений о статусах заказов. Домен сообщает статус, но не изменяет его. |

Персонализация предполагается простой: выше показываются товары из категорий, которыми интересовался покупатель при поиске и покупках. Для нового пользователя показываются новые и самые популярные товары.

## 4. Распределение доменов по сервисам

Все шесть доменов находятся в одном backend. Его можно рассматривать как единственный серверный сервис проекта. Веб-приложение отвечает только за интерфейс, а внешняя система оплаты проводит платежи.

Такое объединение выбрано потому, что в условии нет требований к независимому масштабированию или выпуску частей системы. Одно приложение проще запускать, проверять и сопровождать. Логические границы доменов сохраняются в документации; создавать отдельные файлы, процессы или контейнеры для каждого домена на этом этапе не требуется.

Веб-приложение, backend и база - контейнеры C4. Домены внутри backend отдельными контейнерами не являются.

## 5. Владение данными и взаимодействия

Базой данных владеет только backend. Другие приложения не обращаются к ней напрямую, поэтому разделяемой между сервисами базы нет. Внутри backend ответственность за данные распределена следующим образом:

| Домен | Данные |
|---|---|
| Пользователи | ID пользователей, информация профиля в зависимости от роли. |
| Каталог | Товары, ID продавцов, категории, характеристики, фото и текущие цены. |
| Рекомендации | Поисковые интересы и предпочтения пользователя. История покупок получается из области заказов. |
| Заказы | ID покупателя, позиции заказа, ID товаров и продавцов, описание и цены в момент покупки, количество, дата и статус. |
| Платежи | ID заказа, сумма и валюта платежа, ID платежа у провайдера, попытки оплаты и их результаты. |
| Уведомления | ID получателя, ID заказа, текст сообщения. |

Каталог хранит текущую цену, а заказ - цену на момент оформления. Поэтому изменение товара не меняет ранее оформленный заказ. Платежи учитывают результат оплаты, а изменение статуса заказа относится к ответственности заказов.

| Взаимодействие | Способ и назначение |
|---|---|
| Веб-приложение → backend | Синхронный HTTPS/JSON: работа с товарами, профилем, заказами, лентой и уведомлениями. |
| Backend → PostgreSQL | Синхронные запросы к БД: чтение и запись данных. |
| Заказы → Каталог | Синхронный вызов внутри приложения: получение названия, цены и продавца товара. |
| Заказы → Платежи | Синхронный вызов внутри приложения: передача заказа и суммы для начала оплаты. |
| Backend → система оплаты | Синхронный HTTPS-запрос: создание платежа. Ответ на создание не означает успешную оплату. |
| Система оплаты → backend | Асинхронное уведомление HTTPS webhook: отдельный запрос с результатом оплаты. |
| Рекомендации → Каталог и Заказы | Синхронные вызовы внутри приложения: получить товары и сведения о прошлых покупках. |

Внутренние вызовы выполняются в одном процессе, без сети и брокера. Асинхронность webhook означает, что результат оплаты приходит позже отдельным запросом.

В монолите собственных внутренних сервисов нет: здесь показаны связи контейнеров, доменов и внешней системы.

## 6. Альтернативные варианты декомпозиции

Рассмотрены два существенно разных варианта: единый модульный монолит с общей для него БД и шесть микросервисов с отдельными базами. Подробное описание находится в [option.md, пункт 6](option.md#6-альтернативные-варианты-декомпозиции).

## 7. Компромиссы вариантов

Монолит проще запускать и сопровождать, но его части выпускаются и масштабируются вместе. Микросервисы дают независимость выпуска и масштабирования, но требуют обработки сетевых сбоев и согласования данных между базами. Подробное сравнение - в [option.md, пункт 7](option.md#7-плюсы-минусы-и-компромиссы).

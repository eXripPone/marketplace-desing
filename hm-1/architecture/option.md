# Варианты архитектуры и выбор решения

## 6. Альтернативные варианты декомпозиции

### Вариант A: модульный монолит

Одно backend-приложение содержит шесть логических областей: пользователей, каталог, рекомендации, заказы, платежи и уведомления. Все они используют одну PostgreSQL, при этом у каждого домена определены собственные данные и ответственность. Общение между областями происходит вызовами функций внутри приложения.

Веб-приложение обращается к backend, а backend - к внешней системе оплаты. Отдельные сервисы и брокер сообщений не нужны. Именно этот вариант показан на приложенных C4-диаграммах.

### Вариант B: микросервисы

Каждый из шести доменов становится отдельным приложением со своей базой данных. Например, заказы получают текущую цену через API каталога. Результаты оплаты и изменения статуса заказа могут передаваться через брокер сообщений.

Сервисы выпускаются независимо и не читают чужие базы напрямую. В отличие от монолита, взаимодействие между доменами проходит по сети, а данные распределены между отдельными хранилищами.

## 7. Плюсы, минусы и компромиссы

### Модульный монолит

**Плюсы:** один backend проще собирать, запускать и отлаживать. Внутренние вызовы не зависят от сети. При необходимости согласованные изменения в общей БД можно выполнить в одной транзакции. Для учебного проекта требуется мало инфраструктуры.

**Минусы:** изменение одной части требует выпуска всего backend. При росте нагрузки на рекомендации масштабировать приходится всё приложение. Сбой внутри одного процесса может повлиять на остальные функции. Границы доменов нужно соблюдать дисциплиной разработки.

### Микросервисы

**Плюсы:** каталог или рекомендации можно масштабировать отдельно. Команды могут выпускать сервисы независимо при сохранении совместимости API. Отдельные базы делают владение данными явным.

**Минусы:** нужно сопровождать несколько приложений и баз. Появляются сетевые задержки, таймауты, повторные запросы и необходимость наблюдать распределённые операции. Изменения между базами не объединяются простой общей транзакцией, поэтому данные могут временно расходиться. События могут доставляться повторно и требуют соответствующей обработки. Независимость частей системы достигается ценой более сложной инфраструктуры и согласования данных.

## 8. Обоснование финального выбора

Выбран **модульный монолит**. Все функции кейса можно разместить в одном backend с явными границами ответственности. Требований к отдельным командам, большой нагрузке или независимому развёртыванию доменов в условии нет, поэтому сложность микросервисов пока не оправдана.

Простые рекомендации и уведомления внутри приложения не требуют выделенных сервисов. Единая база принадлежит только backend, а владение данными внутри него зафиксировано по доменам. Цена выбора понятна: приложение выпускается и масштабируется целиком.

Ограничение «без бизнес-логики» определяет объём реализации, а не запрещает какой-либо архитектурный вариант. Поэтому сейчас создаётся только один файл приложения с `/health`, который запускается в Docker. Домены, веб-интерфейс, PostgreSQL и платежи остаются на уровне проектирования.

Для текущего задания монолит проще и достаточен по функциональным требованиям. В будущем решение можно будет изменить, если потребуется.
